# Supabase 反代部署清单（一次性，约 1 小时，除域名外全免费）

## 为什么要这一层

境内直连 `*.supabase.co` 会被 SNI reset（本机强制直连实测 21/21 次失败），
但境内直连 Cloudflare 边缘是通的。所以让浏览器只访问**自己域名的入口**，
由 CF 边缘去连 Supabase。代码里 `VITE_SB_URL` 是唯一出口，换地址不用改一行逻辑。

前端已经上线了：`https://oqdbpo.github.io/family-menu/` —— UI、图标、离线壳都能加载，
但家人打开只会看到设计好的「正在叫醒厨房」态。**做完这份清单，数据才通。**

花费：一个域名，.com 约 ¥70/年，.top/.xyz 首年 ¥10–20。Cloudflare 免费档够用
（Worker 10 万请求/天，自定义域名绑定免费）。

---

## 第 1 步：买域名

注册商任选，能自由改 nameserver 即可：

| 注册商 | 实名认证 | 备注 |
|---|---|---|
| Cloudflare Registrar | 不需要 | 成本价卖 .com，但要信用卡，且必须先把域名加进 CF 账号 |
| Porkbun / NameSilo | 不需要 | 支付宝可用（Porkbun），续费透明 |
| 阿里云 / 腾讯云 | **需要，1–2 个工作日** | 微信付款方便，但实名要等 |

- 建议直接买 `.com`。`.top` `.xyz` 首年便宜但续费翻倍，且廉价 TLD 在国内解析稳定性更差。
- **不需要 ICP 备案**：站点和内容都在境外（GitHub Pages + Cloudflare + Supabase），不指向境内服务器。
- 挑一个短的好记的子域前缀，比如以后用 `menu.你的域名.com`。域名本身别用来做别的。

## 第 2 步：把域名接入 Cloudflare

1. 注册 Cloudflare 免费账号 → **Add a site** → 填裸域名（`你的域名.com`）→ 选 **Free** 计划。
2. CF 给你两个 nameserver（形如 `ana.xns1.cloudflare-dns.com`）。
3. 回第 1 步的注册商，把域名的 NS 从默认改成这两个。
4. 等生效（几分钟到几小时）。验证：

```bash
dig +short NS 你的域名.com @8.8.8.8      # 或 nslookup -type=NS 你的域名.com
# 看到 cloudflare-dns.com 字样就成了，CF 后台会发邮件说 site is active
```

## 第 3 步：部署 Worker

**推荐控制台粘贴，零本地依赖：**

1. Workers & Pages → **Create** → Worker 分类 → **Get started** → 名字填 `family-menu-proxy` → Deploy。
2. 打开 **Edit Worker**，把 `worker/src/index.js` **全文替换**进去 → **Save and Deploy**。
3. ⚠ **关键：控制台部署不会读 `wrangler.toml`**，那两个变量必须手填：
   Workers → `family-menu-proxy` → **Settings → Variables and secrets → Add variables**

   | 变量名 | 值 |
   |---|---|
   | `SUPABASE_PROJECT_REF` | `myawyxhhllvsdpqabnro` |
   | `ALLOWED_ORIGINS` | `https://oqdbpo.github.io,http://localhost:5173,http://127.0.0.1:5173` |

   （想省这一步就改用 CLI：`npx wrangler login && npx wrangler deploy`，它会读 wrangler.toml。）

4. **不要**加任何 secret。这个 Worker 不含密钥，`sb_secret_...` / `service_role` 永远不该出现在这里。

## 第 4 步：绑自定义域名

1. Workers → `family-menu-proxy` → **Settings → Domains & Routes → Add → Custom domain**。
2. 填 `menu.你的域名.com` → CF 自动在 DNS 里建记录并开启代理（橙色云）。
   **橙色云必须开**——灰色云等于把 `supabase.co` 直接暴露给访客，等于白做。
3. Zero Trust 后台 → SSL/TLS → 模式选 **Full (strict)**（默认 Flexible 也常能用，但 strict 省事）。
4. 证书自动签发，等 1–2 分钟。

## 第 5 步：验证（**别跳过，这一步决定要不要继续**）

在**这台电脑上**跑（它的直连结果等价于家里 WiFi 下的设备）：

```bash
curl --noproxy '*' -sS https://menu.你的域名.com/healthz
# 期望：proxy ok / upstream https://myawyxhhllvsdpqabnro

curl --noproxy '*' -sS -o /dev/null -w '%{http_code}\n' \
  -H "apikey: $(grep '^SB_ANON_KEY' supabase/.env.local | cut -d= -f2)" \
  "https://menu.你的域名.com/rest/v1/dishes?select=id&limit=1"
# 期望：200
```

`--noproxy '*'` 是必须的：这台机器开着系统代理 `127.0.0.1:7897`，
不加这个参数测出来的"通"是代理的功劳，不是真实结论（这个误判我犯过一次，README §31.1 有记录）。

**再拿它打一次真实接口**（期望结果已经过联调确认，别看到空数组就以为坏了）：

```bash
curl --noproxy '*' -sS \
  -H "apikey: $(grep '^SB_ANON_KEY' supabase/.env.local | cut -d= -f2)" \
  "https://menu.你的域名.com/rest/v1/dishes?select=name&limit=2"
# 期望：[]        ← 正常。RLS 生效：你这个 curl 请求没有登录会话，不属于任何家庭，
#                   所以查得到表、拿不到行。反代若不通会是 502 或超时，不是 []
```

联调时我在本机走代理验过一遍真实上游，五条路径的表现是：

| 路径 | 结果 | 说明 |
|---|---|---|
| `/auth/v1/settings` | 200，`"anonymous_users":true` | 匿名登录开关确实开着 |
| `/rest/v1/` | **401 `Secret API key required`** | Supabase 的设计，OpenAPI 根只认密钥。**不是反代的锅**，别拿它做健康检查 |
| `/rest/v1/dishes?select=name&limit=2` | 200 + `[]` | 上面那条，RLS 正常 |
| `/storage/v1/object/public/...`（不存在） | 400 内嵌 `404 not_found` | Supabase 自己的响应，转发正常 |
| 白名单外的路径 | 404 `path_not_proxied`，不回源 | 拦截生效 |

**然后再用手机的移动网络（关掉 WiFi）打开一次 `/healthz`** —— 运营商网络是另一个出口，
和家里 WiFi 不是一回事，两边都通才算数。

## 第 6 步：切前端

只改一个 Variables 值，然后重新部署：

1. GitHub → `oqdbpo/family-menu` → Settings → Secrets and variables → Actions → **Variables**
   → 编辑 `SB_URL` → 改成 `https://menu.你的域名.com`（**结尾不要带 `/`**）→ Save。
2. Actions → `deploy-web` → **Run workflow** → Run。构建时会把新地址打进 JS 包。
3. 手机重进一次页面（`registerType: 'autoUpdate'`，Service Worker 会自动换新）。

代码侧已经预留好了，无需改动：
- `src/config.js` / `src/lib/supabase.js` 只读 `VITE_SB_URL`
- `src/lib/supabase.js` 的 `publicImageUrl()` 跟着 `SB_URL` 拼，图片自动走反代
- `vite.config.js` 的 workbox 规则按 `VITE_SB_URL` 的 hostname 匹配，换域名后照样命中

## 第 7 步：这两处**不要**跟着改

| | 保持 | 原因 |
|---|---|---|
| `.github/workflows/keepalive.yml` | 直连 `*.supabase.co` | GitHub runner 在海外，直连更快更稳，少一层依赖 |
| `supabase/verify.mjs` 等本地脚本 | 直连 + 走本地代理 | 它们测的是数据库本身，不是访客链路 |

## 第 8 步：换图后图片没更新

菜品图的边缘缓存是 24 小时。Cloudflare → 你的域名 → **Caching → Configuration → Purge**
→ **Purge Everything**（或只填那张图的 URL）。

## 如果第 5 步实测不通

说明这个域名当前走的 CF 共享 IP 在你所在的运营商线路上被干扰了。按代价从低到高：

1. **换个 CF 节点 IP 段**：先 Purge + 开关一次橙色云，有时重解析就好了；也可以等几小时再试。
2. **换个域名**：不同域名的 CF 解析结果可能不同，最便宜的一次尝试。
3. **Cloudflare 付费套餐 / Spectrum（¥160+/月）**：能拿到独立 IP，效果好但成本高，家庭项目不建议。
4. **回到微信生态**：小程序云开发约 ¥239/年起，境内直连没问题，但 `src/` 要按 uni-app 重写。

到第 3 步就不划算了——那时方案 B′ 的"免费"前提已经不成立，应该重新评估。
